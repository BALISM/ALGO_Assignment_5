Q4 (a)  PROOF: Any MST T can be produced by Kruskal's Algorithm
==============================================================================

Claim
-----
  Let G = (V, E, w) be a weighted undirected graph and let T be any
  minimum spanning tree of G.  Then there exists a total ordering of
  the edges of E (consistent with non-decreasing weights) such that
  Kruskal's algorithm, using that ordering, outputs exactly T.

Background: how Kruskal's algorithm processes ties
--------------------------------------------------
  Kruskal's algorithm processes edges in non-decreasing weight order.
  When multiple edges have the same weight, the algorithm may choose
  among them in any order.  Different orderings among tied edges can
  produce different spanning trees, all of which are MSTs (they all
  have the same total weight).

Proof
-----
  Let T be an arbitrary MST of G.  We construct an edge ordering sigma
  such that Kruskal(sigma) = T.

  Step 1 - Partition the edges by weight.
    Let w_1 < w_2 < ... < w_k be the distinct edge weights.  Let
    E_i  = { e in E : w(e) = w_i }  and
    T_i  = { e in T : w(e) = w_i } (the MST edges at weight w_i).
    By the MST cycle-cut property, T_i is a subset of E_i.

  Step 2 - Order edges within each weight class.
    Within E_i, list the edges of T_i FIRST (in any order among themselves),
    followed by the edges of E_i \ T_i (in any order).
    Concatenating these ordered groups for i = 1, 2, ..., k gives sigma.

  Step 3 - Show Kruskal(sigma) = T.
    Kruskal processes edges in the order sigma.  We track the DSU state
    after processing each weight class.

    Invariant (maintained by induction on weight class i):
      After processing all edges of weight <= w_i, the edges accepted by
      Kruskal are exactly the edges of T with weight <= w_i, i.e.,
      T_1 union T_2 union ... union T_i.

    Base case (i = 0): trivially true (empty set).

    Inductive step (weight class w_i):
      Assume the invariant holds after weight class w_{i-1}.
      We process E_i in the order: T_i edges first, then E_i \ T_i edges.

      (a) Each edge e = (u, v) in T_i is considered.
          Since T is a spanning tree and the edges accepted so far form
          a forest that is a subgraph of T, the components of the current
          DSU are exactly the connected components of the subgraph
          T[V, T_1 union ... union T_{i-1}].  Every edge in T_i connects two
          different components in that forest (otherwise T would contain
          a cycle, contradicting that T is a tree).  Therefore DSU.find(u)
          != DSU.find(v), so Kruskal ACCEPTS e.  After processing all of
          T_i, the accepted edges are T_1 union ... union T_i.

      (b) Each edge e = (u, v) in E_i \ T_i is considered.
          Adding e to T would create a cycle C in T.  All edges of C
          lie in T; those with weight < w_i were accepted in earlier
          rounds, and those with weight w_i are in T_i (all accepted in
          step (a) above).  Therefore u and v are already connected in
          the current DSU forest, so Kruskal REJECTS e.

      After processing all of E_i the invariant holds for class i.

    By induction the invariant holds for all i.  After processing all
    edges the accepted set is T_1 union ... union T_k = T.  Hence Kruskal(sigma)
    outputs exactly T.                                              QED

Corollary
---------
  Every MST of G is a possible output of Kruskal's algorithm for some
  tie-breaking rule.  Equivalently, the set of Kruskal outputs (over all
  tie-breaking rules) is exactly the set of all MSTs of G.

Q4 (b)  FAST IMPLEMENTATIONS WITH BOUNDED INTEGER WEIGHTS
==============================================================================

We consider two ranges of integer weights:
  (R1) weights in { 1, 2, ..., |V| }  -- range proportional to V
  (R2) weights in { 1, 2, ..., W  }   -- constant range W

The key observation is that INTEGER edge weights allow COUNTING SORT
(or RADIX SORT) instead of comparison-based sorting, breaking the
O(E log E) comparison barrier.


------------------------------------------------------------
Q4 (b-i)  PRIM'S ALGORITHM WITH BOUNDED INTEGER WEIGHTS
------------------------------------------------------------

Standard Prim (binary heap): O((V + E) log V).

Case R1: weights in { 1 .. |V| }
  Replace the binary min-heap with a VAN EMDE BOAS TREE (vEB tree)
  supporting insert, decrease-key, and extract-min in O(log log V)
  amortised time when keys are integers in { 0 .. V-1 }.

  Time with vEB tree: O((V + E) log log V)

  Alternative -- BUCKET QUEUE (also called a DIAL's queue):
  Maintain an array of |V| buckets indexed by edge weight.
  insert and decrease-key: O(1)   (write to bucket)
  extract-min: O(|V|) worst case (scan buckets), but O(1) amortised
               if the current minimum pointer advances monotonically.

  Time with Bucket Queue: O(V + E + |V|) = O(V + E)
  (the |V| term arises from scanning at most |V| buckets total).

  Therefore, with weights in { 1 .. |V| }:
      PRIM can run in O(V + E)  using a bucket-queue priority queue.

Case R2: weights in { 1 .. W } for constant W
  The bucket queue now has only W buckets.
  extract-min scans at most W buckets: O(W) = O(1) amortised.
  Total time: O(V + E + W) = O(V + E)  (W is a constant).

  Therefore, with weights in { 1 .. W } (W constant):
      PRIM can run in O(V + E).

Summary for Prim
  +--------------------------------+---------------------------+
  | Weight range                   | Best achievable time      |
  +--------------------------------+---------------------------+
  | Arbitrary reals / no bound     | O((V+E) log V)  [binary heap] |
  | Integers in { 1 .. |V| }       | O(V + E)        [bucket queue] |
  | Integers in { 1 .. W }, W=const| O(V + E)        [bucket queue] |
  +--------------------------------+---------------------------+

------------------------------------------------------------
Q4 (b-ii)  KRUSKAL'S ALGORITHM WITH BOUNDED INTEGER WEIGHTS
------------------------------------------------------------

Standard Kruskal (comparison sort + DSU): O(E log E).

The bottleneck is edge sorting.  With integer weights we can use
non-comparison sorting to break the Omega(E log E) comparison barrier.

Case R1: weights in { 1 .. |V| }
  Use COUNTING SORT to sort E edge weights in O(E + |V|) time.
  DSU processes E edges in O(E alpha(V)) ~ O(E) time.

  Total time: O(E + V)   (counting sort dominates over DSU).

Case R2: weights in { 1 .. W } for constant W
  Counting sort with W buckets: O(E + W) = O(E)  (W is constant).
  DSU: O(E alpha(V)) ~ O(E).

  Total time: O(E).

  Note: O(E) is essentially optimal since merely reading the edge list
  requires Omega(E) time.

Summary for Kruskal
  +--------------------------------+---------------------------+
  | Weight range                   | Best achievable time      |
  +--------------------------------+---------------------------+
  | Arbitrary reals / no bound     | O(E log E)   [comparison sort] |
  | Integers in { 1 .. |V| }       | O(E + V)     [counting sort]   |
  | Integers in { 1 .. W }, W=const| O(E)         [counting sort]   |
  +--------------------------------+---------------------------+

Comparison: Prim vs Kruskal with Bounded Weights
-------------------------------------------------

  Weights in { 1 .. |V| }:
    Prim   : O(V + E)   (bucket queue)
    Kruskal: O(V + E)   (counting sort + DSU)
    Both achieve the same O(V + E) time -- essentially linear.

  Weights in { 1 .. W } (constant W):
    Prim   : O(V + E)   (bucket queue with W buckets)
    Kruskal: O(E)       (counting sort + DSU, O(E) dominates)
    Kruskal has a slight edge because V is absorbed by E when the
    graph is connected (E >= V-1), so both are effectively O(E).

  Space for both algorithms remains O(V + E) in the adjacency-list model.

Conclusion
----------
  Bounded integer edge weights allow linear-time (or near-linear)
  MST construction using non-comparison sorting for Kruskal and
  bucket-queue priority queues for Prim.  When weights are integers
  in { 1 .. W } for a constant W, both Prim and Kruskal run in O(V + E)
  which is essentially optimal for sparse graphs.
